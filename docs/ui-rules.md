# Themis UI rules

Follow the [product design rules and color system](../DESIGN.md), including **Only what earns its place**: every visible element must tell the person something about the current task or let them act, on every screen. Polish the existing workspace; preserve its conversation and review workflows.

- Keep a permanent icon-only utility rail. Each icon has one clear tooltip and accessible name. The expandable dock contains Themis, New chat, a project switcher and one Chats list for the chosen project (most recent first, 12 shown, then Show more) under a small, dimmed, divided CHATS label with a count, so the label never reads as a chat row. Each chat row has a speech-bubble icon in the folder-icon column so titles align with the project name, and the active chat sits in a soft pill. Project names and chat titles that do not fit scroll slowly to their end and back; reduced motion wraps them instead. The switcher lists projects, marks projects with live work, and ends with New project. Every project row shows, always visible and side by side, a Rename icon, a Delete icon and its chat count; the icons act on that row's project without switching to it. The built-in Themis project has no Delete icon (an empty slot keeps the counts aligned); Delete asks for confirmation and says the folder moves to the Trash; projects live in the fixed projects folder, so there is no Open folder action. Long project names in the menu stay inside it and reveal on hover. Thread rows show an indicator only for live work (spinning arc), waiting for approval (pulsing pause), failure (red alert) and a run that finished in the background and has not been opened yet (green check, cleared on open). Dragging the sidebar or Workspace edge moves only the width and commits it on release; a thin accent line marks the edge on hover, and double-click resets it. Opening Workspace on a window narrower than 1500 px folds the sidebar to its rail and closing Workspace restores it. Animate its width with the canvas so collapse/expand moves smoothly; reduced motion uses an immediate toggle.
- Keep Themis in the sidebar at `~/ThemisOS/Projects/Themis`, without a lock or name protection. All new projects live under `~/ThemisOS/Projects`. No setting or creation action changes this root. Settings shows only the shared projects root. Renaming any project, including Themis, changes its display name only; folders and history stay in place. Existing folders are never moved automatically.
- Popovers (the model and effort pill, the composer's + and approval menus, the project switcher, the context panel) close on a click anywhere outside them or on Escape; a `<details>` popover carries `data-popover`. Inline expanders in the conversation are not popovers and stay open.
- The composer carries one box at a time (canvas board D): the goal as one row, then an approval, else the oldest open question; what waits behind it is a count, never a second box. All of it folds to one row of pills (remembered). An approval is never a modal and covers nothing; other waiting chats show **Needs approval** in the sidebar. Once decided it goes away and leaves nothing in the chat. An answered or skipped question leaves the composer for a one-line note in the turn where it was asked, never a strip at the top of the chat. An approval is decided only by its buttons or their number keys 1/2/3 while focus is inside that box (after a click or Tab into it): a digit typed anywhere else, such as in the composer, never decides it; Escape and stray clicks never do either.
- Edit thread changes only its name. The thread header's model pill selects the model and reasoning effort between runs. Each completed response displays its captured model, including after restart or a later switch. Never infer old response models from the current selection; use “Model not recorded” for missing historical metadata.
- Use dark mode only. Offer 17 coordinated templates, including GitHub Dark and Dimmed, plus 12 local font choices and 12–22px text sizes. Preview changes throughout the app; Apply saves, Revert or leaving Settings restores saved choices. Code remains monospace.
- Buttons are unboxed: text or icon only, no filled or outlined containers. Primary actions use the accent color; selection uses brighter, bolder text. The composer is one rounded pill with a **+** menu (attach, skill, plugin), the YOLO/Custom shield, the context meter and send, and a quiet row showing the project directory and current Git branch. Cards group a meaningful unit (an automation, a review item, a settings section, an integration tile). Keep settings labels short while retaining necessary permission explanations.
- Show the selected thread with bright, bold text, without a background or colored side stripe. Thread options (rename, remove) live in a ⋮ menu revealed on hover or focus. Use continuous surface layers in every palette: lighter icon/header frame, dark collapsible sidebar, darker canvas. Separate them through their backgrounds, without bright outlines or frame gutters. Appearance swatches show this same order; the app itself is the preview.
- Overflowing project and thread names start at the beginning, then move right to left on hover or keyboard focus. Preserve their full accessible names. Reduced motion wraps titles and disables motion and shimmer.
- Use the Honey, Pearl and Ink **Bubbles** artwork (bubble blobs drawn from the original blob knight body) for startup and the optional floating companion. Keep other UI surfaces free of companion decoration; retain native app icons and favicon and the glinting Themis wordmark in the expandable dock.
- Put a Bubbles icon in the permanent left rail. One click opens a small popover with the three variants, a Companion checkbox and a 56–192px size slider; the icon reflects the selected variant and stays available when hidden or the dock is collapsed. Remember variant, visibility, size and position locally. On desktop, use a separate transparent always-on-top window that moves outside Themis and over other apps. Provide a visible drag grip, free positioning and keyboard arrow movement; follow the global mouse position with its gaze. Browser previews stay within the canvas above the composer. Use no edge snapping or surrounding container. Speech is limited to two short state notes: “All done!” for about six seconds after completion and “Needs you” while approval or an error needs attention. Closing the main window also closes the companion. Respect reduced motion for blinking, breathing, gaze and reactions.
- Startup shows the selected bubble while preferences, workspace and conversation restoration actually run; no artificial loading delay or progress percentage. Failures dismiss the loader and retain the existing error notice. The companion reacts to the selected conversation's running, completed and approval/error states. Pointer and keyboard interactions remain available without motion.

Verification belongs in [UI polish checks](ui-polish-verification.md); appearance details are in [Desktop appearance](appearance.md).
- New chats show a greeting (“Hi there.” in the warm gradient, then the project question), the composer centred, and up to four starter chips (project skills first). The first message moves the composer to the bottom.
- The agent's progress sentences stay visible, styled like its answers; the tool calls between them fold into one “N tool calls” row, which stays folded during a run so the chat does not jump. Completed replies offer Copy beside their model label and the run's duration. A steered message is a plain user bubble with no label. A context checkpoint renders as a centred “Context compacted · before% → after%” divider; before is the usage that triggered it (the runtime reports it just before compacting), after is the first usage reported after it.
- The composer's context meter shows byte-estimated usage of usable message space from the runtime's `context_budget` events. Its popover breaks usage into tool activity, messages, attachments, checkpoint and task ledger, and system instructions, lists tool-definition, reply and safety reserves held outside the bar, and states the tidy-up and auto-compact thresholds. When the chat has recorded requests, one note under the legend reads "This chat so far: 1.25M in · 40.2k out · 54 requests" (read when the panel opens). While a run is active and growth projects compaction, the chip turns warm and a dismissible heads-up appears once above the composer. There is no manual compaction or retry control.
- **Resource use** sits at the right of the window title bar: CPU (Themis's share of all cores), memory and the window's frame rate, each a 13 px icon and a tabular number in the dimmest text color, amber when CPU is at least half the machine, memory grew steadily for 30 minutes, or the window draws under 30 frames a second. It is hidden until the first sample and polls every 5 s only while the window is visible. One click opens a small table (part, CPU, memory) for the app, the built-in browser and tools, a line for any group whose memory keeps growing, and one note on how CPU is counted; a click outside or Escape closes it. There are no charts, logs or settings in it.
- **Workspace** in the thread header opens a monitor of what agents write, not a review or Git-action surface: Changes (folder-grouped changed files, with a filter only for long lists, beside a unified diff that stays live, see Live changes), Files (project tree and read-only file view), Branches (local branches, upstream and tracking; clicking another branch shows what it adds to the current one, read-only) and Pull requests (open PRs from the GitHub CLI when installed and signed in, otherwise the reason). One lean header row holds the tabs as icons, each named by a tooltip below it and its accessible name, with small count badges on Changes and Tasks, and a panel-close icon; the project and branch are not repeated there, since the composer shows them. The views keep thin edges so the page and the diff get the room. Its width is adjustable by drag or arrow keys and remembered, down to a 260 px chat; the Browser tab keeps only a thin edge around the page. Its state-changing controls are Stop and Pause on Tasks rows and the Browser tab's own controls, which never change project files; a new one belongs here only when it is necessary or clearly reasonable for the person (see AGENTS.md).
- **Idle browser pages.** The built-in browser draws on the CPU, so a 3D page takes several cores. When a run ends, or the person leaves the Browser tab, the chat's pages freeze until the next agent action, input or view of the tab. They do not freeze while the person watches the Browser tab or a recording runs. Scripts and screenshots still work on a frozen page; sound stops.
- **Browser** is the sixth Workspace tab: the chat's built-in browser, the same tabs the agent's `browser_*` tools drive, streamed from a headless Chromium at the view's size. It remembers its own panel width (760 px default). With `browser.open_workspace` on (off by default), the agent's first browser step in a run opens Workspace on this tab for the chat on screen; later steps in that run leave the panel as the person left it. Otherwise the overview box shows the browsing as a live preview. The toolbar has Back, Forward, Reload (disabled when there is nowhere to go), the address field (Enter opens it; a bare host gets `https://`, `localhost` gets `http://`) and DevTools, which shows a red console-error count only when the page has errors. A tab strip appears only with two or more tabs. While the agent acts, one line shows a spinner and "Agent is clicking “Create account”". The person and the agent use the page at the same time: clicking, typing, scrolling or typing an address goes to the page and never pauses the agent; there is no take-over or hand-back control. DevTools opens Chrome's own DevTools for the current tab in a split below the page. Empty states: "No page open" (with the address field) and "No Chromium browser found". There is no idle "connected" or "ready" badge. A thin indeterminate loading bar runs under the address field while the page loads, while an address or Back/Forward/Reload the person started has not answered, and while the agent starts the browser; "Loading browser…" shows it too (the first start includes downloading the engine). Reduced motion shows it still. The person's input, addresses and toolbar never wait for an agent action in progress, and the stream and title follow every navigation, including to another site. **Sound** (speaker, crossed out while off) starts off for each chat; turning it on lets the chat's pages play through the Mac's speakers (the stream itself carries no audio, and recordings stay silent). **Capture** (camera) adds a screenshot of the visible page to the composer's pending attachments; **Record** (circle, red while recording) starts a recording, and stopping one adds the video the same way. While anything records, a red line above the page reads "Recording 0:12 · started by you · stops at 2:00" (or "started by agent") with **Stop**, the page frame turns red, and a red pill with a pulsing dot and the time sits left of the Workspace button in the thread header on every tab and with Workspace closed; it opens the Browser tab. Reduced motion stops the pulse.
- **Media in replies.** Images, videos and PDFs an agent attaches (`attach_file`) sit under its reply, in order, as plain thumbnails with no card around them (112 px tall at the item's own shape, at most 200 px wide, a hairline edge and a one-line muted caption): up to four in a row, five or more as three thumbnails and a **+N** tile. Video tiles show the first frame and a play mark. A tile opens the viewer: caption, file name when there is a caption, "2 of 9" across the chat's attached media, Previous/Next and arrow keys, Escape or ✕ to close. Screenshot thumbnails of tool calls are not part of the viewer.
- **Goal status in the chat.** The goal says what it is doing in plain, muted sentences with no box or label: starting, paused, resuming, removed, checking a turn's claims ("I'm checking that against the goal now."), "That isn't proven yet, because…, so I'm carrying on.", a failed turn and its retry, and pausing after failures. The agent speaks for itself inside its turns.
- **Colour in the chat.** Replies, notes, links, the edited-files card and the running ring stay neutral, so colour marks only what needs the person: an approval's actions, the Send button and the YOLO warning. Links are underlined rather than blue. Diff views keep their green and red.
- **Links in replies.** Web addresses open in the chat's Browser tab, also when written as code. Links are for evidence: a file cited by line in code (`src/app.ts:12`) or a file the reply attached is highlighted and opens in Workspace, its diff if this chat changed it, otherwise Files. A file named in passing stays plain code.
- **Chat column width.** Messages and the composer share one column that follows the room the sidebar and Workspace leave: 90% of the chat's width, at least 740px and at most 1120px so lines stay readable, narrower only when the chat itself is. It keeps clear of the overview box. Reply prose is justified with hyphenation, so its right edge is even.
- **Chat overview box.** While Workspace is closed, a compact box floats over the top right of the chat whenever it has something to list. The chat keeps its room from the first message, so a long reply never jumps narrower (24% of the chat's width, from 220 to 300 px, icons only at 48 px when folded or in a chat narrower than 760 px) and the reading column and composer move left to leave it room. Its header holds the Workspace icon (opens Workspace on its remembered tab; closing Workspace brings the box back) and a fold chevron (remembered). An open browser page shows first as a live preview (frames at most 440 px wide from a preview screencast that never resizes the page; a caption with the page title or "Agent is …" and a gold dot while the agent drives it; it opens the Browser tab), replaced by a Browser row when folded or narrow. Then one 34 px row per part of the chat that has something to show, each an icon, a value and a tooltip, opening that Workspace tab: Changes (files and +added −removed lines), Tasks (running, needing you, queued; a dot when something needs you), Artifacts (the latest media file and a count; opens it in the chat's viewer). Cost is shown only in Settings › Usage. A row with nothing to show is left out, and so is the whole box. It changes nothing itself.
- **Links in replies.** A plain click on an `http(s)` link in a reply opens it in the chat's built-in browser (the agent keeps working) and shows the Workspace Browser tab; Cmd/Ctrl-click opens the system browser. Other links are unchanged.
- **Tasks** is the fifth Workspace tab, with a small count of items that need attention, run or are scheduled. It covers the current chat only and groups rows as Needs attention (a run waiting for approval, an unseen failed automation run), Running, Scheduled (this chat's automations; paused ones are listed without buttons and are resumed in Automations) and Earlier (recent finished or failed automation runs, plus automations that ended, newest first, with the reason: completed by agent, expired, run limit, failed 3 times, chat deleted or deleted; a past run keeps its automation's name and "by agent" tag after deletion). A Scheduled watch row reads like "Every 2 min · until status.txt says DONE · expires 21:30 · next ..."; a user's automation paused by the failure backstop reads "Paused · failed 3 times". A row has a status icon, name, kind tag (Run, Automation · continues this chat, Automation · by agent), a meta line (schedule, next run, last result) and Stop (stops the chat's current run) and/or Pause (turns the automation off). The footer reads "Shows this chat only. Stopping never undoes work already done." Background shell tasks started by the agent appear as rows too (see below); conversation notice cards are not shown.
- A **background task row** (`BackgroundTaskRow`) shows the command in monospace, the tag "Background task", a meta line ("Started 14:05 by agent · ends when this chat closes · port 1420"; the port is read from recent output when present), the last three output lines in an inset block, **Stop** (running only) and **Full log**, which loads the whole bounded 64 KiB log read-only and toggles to "Hide log". Running tasks are listed under Running, timed-out or non-zero-exit tasks under Needs attention, stopped or clean exits under Earlier. A task lost to a server restart is listed under Earlier with "lost after restart; the program may still be running" and is not counted (it cannot be dismissed). **Full log** is hidden when the preview already shows the entire output. The port in the meta line is parsed from recent output (`localhost:N`, `127.0.0.1:N`, `0.0.0.0:N` or "port N") and is omitted when the program prints none. Stop stops only that task. No other task control exists.
- There is no task indicator in the thread header; the Workspace **Tasks** tab label carries the count of active tasks (needs attention, running, scheduled, finished and unseen). The count refreshes from run, approval, tool, automation, review and background-task events (`background_tasks_changed`), never by polling. Running background tasks count as running; timed-out or failed ones as needs attention.

- Utility pages (Integrations, Automations, Review queue) share one centred column with an unboxed title and divided rows instead of cards. Filters stay on one toolbar line; result counts and Reset filters appear only while a filter is active. Automation and Settings on/off choices use switches; secondary row actions appear on hover or focus. Search lists only automations once there are more than four.
- Search (⌘K) is a single borderless field with Chats, Projects and Actions groups, short project names instead of paths, and a short list when the query is empty. Help lists shortcuts with key caps.
- Sent attachments sit above the user's message: images, videos and PDFs as rounded thumbnails, other files as compact chips with their extension. An unavailable preview falls back to the chip.
- The Workspace change list shows only readable text: binary files, compiled artifacts (`.pyc`, `.o`, …), `.DS_Store` and cache folders (`__pycache__`, `node_modules`, `.venv`, …) are left out, and a short note counts what was hidden. Deleted files stay listed. Diffs and the file view wrap long lines under their text column with syntax colours instead of scrolling sideways.
- After a turn ends, its reply lists the files that turn edited (“Edited N files”, with A/M/D status and the folder dimmed). The list compares the project's changed files before and after the run, so edits made with shell commands count, earlier edits do not, and binary or generated files are left out. Selecting a file opens Workspace on that file's diff. The list is saved with the conversation.
- **Run outside the sandbox?** When the OS sandbox blocks a command in Custom, the approval request has tool `shell_unsandboxed` and `command.sandbox_blocked` (the reason, untrusted text rendered with hidden characters escaped). The box is titled "Run outside the sandbox?", names the tool "shell (outside the sandbox)", shows the command chips as usual, says what the sandbox blocked and that outside it the command can write anywhere you can, read secret folders and use the network, and keeps the same buttons and numbering (destructive commands: Allow once and Deny only). "Allow in this chat" lets that command family run outside the sandbox in later runs. YOLO never shows it.
- **Settings layout.** Opening Settings hands the whole left sidebar to Settings' section list, one column at the sidebar's usual width: **Back to app** at the top (the only way back), then the sections (icon and short name: General, Appearance, Models, Usage, Secrets, Permissions, Browser, Web, Advanced). The icon rail is hidden meanwhile. The header and its sidebar toggle stay where they are; the toggle folds the Settings list to icons (named by tooltip and accessible name) exactly as it folds the rail, the width is shared and resizable as usual, so the page does not shift when entering or leaving Settings. Keyboard focus moves to the chosen section on entry and to Home on Back. Elsewhere the rail starts with **Home**, which returns to the chat. The selected section's name is the only heading on the right; each group of rows sits in one quiet rounded container with a small title above it, label on the left and control on the right. No paragraphs: a fact worth keeping becomes the title's or label's tooltip. Group actions (Refresh models, Reset model, Reset limits, Restore defaults) are small icon buttons beside the group title. Appearance shows Revert and Apply only while a preview differs from the saved theme.
- **Settings → Browser** is global and edits only the `browser` block of the user `runtime.jsonc` in place (field-level writes that keep the rest of the file and its comments; the one in-app exception to file-only configuration). Groups: Built-in browser (switch; Browser select with Choose…, shown while on); Agent permissions (three selects; the Allow/Ask/Block meaning is the title's tooltip); Site exceptions (a compact table where unset cells read a dimmed Default, × to remove, an Add site field; Restore defaults beside the title); Developer mode (Enable full CDP access, Show secrets to the agent); Downloads (Save to path with Change… and a reset icon when set, Open Workspace when the agent starts browsing); History and data (one row with Manage… that reveals the project select, history search with Reopen and Remove, and Clear browsing data with its inline confirmation). Debugging's select is disabled while Developer mode is off.
- **Live changes.** The open chat's diff (header count, overview box, Workspace › Changes) stays current wherever a change comes from, and its line counts cover the whole change even when a large file lists only its first lines: about every 1.5 s during a run and 4 s otherwise, slower on a repository where reading takes long, paused while the app is hidden and refreshed when it comes back.
- **Integrations › Discover › Sources** (board 22) lists each marketplace with its plugin count and last check or progress, a switch that shows or hides it in Discover, and Remove with confirmation (not for the official source). Add marketplace has one Source field; Check reads the manifest and shows name, publisher and count with the trust line before Add. Plugins appear as soon as their catalog is known, with the count ("Checking 72/315") beside the filters and "Checking…" on unchecked cards. While checks run, every card stays in its place and the group counts hold, so nothing moves under the pointer; the status filter and sorting apply once checking finishes.
- **Integrations › Installed** (board 23) has the tabs Plugins, Skills, Connections and Hooks with counts, and Update all beside them when a plugin has an update. A plugin row shows its version change (`1.5.5 → 1.6.0`, else "New version") and Update, opens to its parts (each with its own switch and, for a connection, its state), and says "1 part skipped" when that applies. The mcp.json editor and the CLI keep the MCP name.
- **Integrations › Installed › Hooks** (board 24) lists hook events in the order a run reaches them, numbered: Prompt submitted, Run starts, Before a tool runs, After a tool runs, Before context is compacted, Run ends (Subagent starts and Subagent ends join once subagents ship). An event with no hooks is dimmed and reads "None"; clicking an event that has hooks collapses them to its count until you leave the screen. Each hook row shows its name (opens its detail), one line with its plugin, the tools its matcher covers, "Only when it fails" and "Blocks on failure" where they apply, and its switch; there is no separate status text. Below, one line per plugin says which of its hooks were skipped and why in plain words ("2 hooks skipped (guards): unsupported event (SessionEnd); matcher NotebookEdit has no Themis tool."). No activity counts; adding and editing hooks stays in the CLI and `/hooks`.
- **Integrations › Connections** shows one compact row above the list: **Edit as mcp.json**, its status only once a copy is open (Open · saves apply, Applied · integrations, Invalid · line N, or the conflict), and Open with (editor select when more than one is installed) with **Open**. The label's tooltip carries the explanation.
- **Settings → Secrets** is one untitled group with a one-line hint: a row per saved secret, per secret an installed MCP server reads and for the secret OpenCode Go uses (the name in code type, its users such as "OpenCode Go" or `plugin/server` as a small hint, its state Saved, From environment or Missing, and Add/Replace and Remove). Add/Replace opens a masked field with Save and Cancel under the row; the value is never shown. Below the rows, a "New secret name" field with Add. A server card's **Secret needed** · **Add secret** opens this section on that name.
- **Settings → Models** has two groups, Providers first because the model needs one. **Providers**: first the OpenCode Go logo with its status (Checking…, Connected, Key rejected, Couldn't reach OpenCode, Not set), **Check** and **Manage**/**Hide**, which shows the next two rows (open by itself while the key is missing or rejected): **Secret**, a picker of the secrets in Settings › Secrets (`OPENCODE_KEY` by default; an app setting kept across launches); **Value** with Set or Replace (an inline masked field with Save and Cancel) and Remove, and "Saved <secret>" / "Removed <secret>" after the action. The key is checked with OpenCode (no credits) when the section opens, on Check and after any change; the group title's tooltip says where the value comes from and that more providers are added under `"providers"` in runtime.jsonc (Settings › Permissions opens it; no other link or form). Then one row per such provider: its name, its secret's name and its status (Connected, Key set when its models are listed in the file and it has no `/models` to check with, Key rejected, Couldn't reach it, Not set), checked when the section opens and on Refresh models. **Default model**: the model picker with Refresh and Reset, its models grouped by provider (OpenCode Go first; each provider's models under its name, as the provider names them), disabled with "Fix the connection first" until OpenCode Go's key works or another provider is connected. While OpenCode rejects the key, the composer of a chat on an OpenCode Go model says "OpenCode Go rejected the key in <secret>." with **Model settings** (opens Settings › Models) and does not send (a chat on another provider's model is unaffected), and automation model pickers are disabled.
- **Settings → Usage** is read-only. **Tokens · from Themis only** (the title's tooltip says other apps on the same account are not counted) holds one table with a Refresh icon beside the title: rows 5 hours, This week, This month; columns Input (with "· N% cached"), Output (with "· N reasoning"), Requests and, only when some request has a models.dev list price, **≈ List price** ("≈$1.23", a "+" when some requests have no price, "—" when none in that window had one). **Last 30 days** (hidden with no requests) is a stacked daily bar chart by model: the four largest models in the validated categorical colors, or three plus a gray Other; the largest day's total labels the top line, the first and last dates sit below; hovering or focusing a bar shows its date, total, requests and per-model tokens beside the bar; the legend lists each series with its 30-day total and a Free mark for zero-priced models. **Top chats · 30 days** (hidden when empty) lists up to five chats by tokens (title truncated, tokens · requests · estimate) and a dimmed Deleted chats row. No allowance, percentage of a plan, or bill is shown. A store that cannot open shows one alert line.
- **Settings → Web** edits only `web.search_url` in the user `runtime.jsonc` in place. One Search group: Search server (URL field, saved on Enter or leaving it) and Status ("Built-in · " before it when no address is set; Working · N results, No results, JSON output off, Rate limited, Not reachable, or "Not set · web_search is off" when the build has no built-in server, with Check), then the failing engines with their reasons and, for a failure, its one-line fix. The title's tooltip says web_search uses your own SearXNG and fetch_url works without it. Opening the section checks a saved server once.
- **Settings → Permissions** is global and shows three groups. **Approvals**: New chats start in (Custom/YOLO select) and Approval timeout (seconds). **Custom rules**: the effective rules from `runtime.jsonc`, read-only, in order (tool pattern, the risk or command it matches, a source label only for Built-in or Project, and Allow/Ask/Deny), ending with "Anything else" and the default; no editing controls. **Configuration file**: `runtime.jsonc` (full path on hover) with its read status (Loaded, Not created · defaults, Invalid · line N, Unreadable; the one place a "Loaded" status is shown, because it tells the person their edits took effect), and **Open with**: a select of the system text editor plus the code editors installed here (VS Code, Cursor, Windsurf, Antigravity, Zed, Sublime Text, BBEdit, Xcode; remembered as `config_editor`) and **Open**, which opens that one file as plain text in the chosen editor, first writing it if it does not exist, with every setting and preset commented out and explained so the person uncomments what they want (an existing file is never changed). There is no separate example file. Below it appear only problems that change what runs do: the file is invalid or unreadable (with its line; runs are refused), a named sandbox is not available (commands are refused), no sandbox on this system, or the sandbox is off. It shows no rules, sandbox details, project files or chat grants; `themis permissions` prints the full view and the docs explain the rest. This **Open** is the only editor link in the app; there is no in-app configuration editor. The composer shield copy for YOLO reads "No approval prompts; the sandbox still applies."), one ordered list of rules with a short source label (Built-in, User, Project), the sandbox (status and why in one line; when it is on, network, "This project and temporary folders" plus any configured extra writable paths, and a protected line with the secret folders behind a disclosure), the configuration files (path as selectable monospace text, marked only when Not created or Invalid with the problem and its line) and, only when the open chat has grants, Allowed in this chat with the file to edit. It does not show temp or protected absolute paths, what the sandbox covers, other systems' backends, "Loaded"/"On" badges or a separate banner for a file error; those are in [the sandbox docs](sandbox.md). It has no buttons, inputs, switches or editor links. The composer shield copy for YOLO reads "No approval prompts; the sandbox still applies."
- **Approval dialog.** Buttons are **Allow once (1)**, **Allow in this chat (2)** and **Deny (3)**; destructive requests (`grantable: false`) show only **Allow once (1)** and **Deny (3)** (the numbering never changes; 2 does nothing there) plus a fixed sentence that the action always asks. "Allow in this chat" is worded from the approval event's structured `grant_scope` (raw argv tokens plus whether later arguments are covered), derived from the same prefix as the grant key. For `shell` the dialog shows each covered token as its own monospace chip (tokens with whitespace are quoted, control, bidi and zero-width characters appear as `⟨U+XXXX⟩`, at most 12 tokens of 80 characters, with explicit "…(+N more)" markers) followed by "and any further arguments" when a program + subcommand prefix is covered; the sentence is fixed text, never built from argv. Other tools say the grant covers "this tool", and MCP tools say it covers every tool of that server. A request that times out is removed by the `approval-expired` event with the note "Approval expired — the action was skipped". There is no UI for revoking chat grants (edit the chat's grant file or start a new chat); the 500 ms digit delay applies. Digits 1/2/3 decide only outside the composer and form fields.
- **Interrupted runs.** Stop or a failure keeps the text already streamed as an assistant message marked "Stopped by you" or "Interrupted by an error" (saved in the transcript as streamed text before the terminal event, so it reloads the same), followed by the usual Stopped/Request failed note.
- **Composer.** Single-key shortcuts never fire from the composer, the shield or form fields. A mouse press on the shield does not move focus to it; the Approval mode select ignores typed letters (arrows, Space and click still work); clicking the box outside its controls focuses the text area.
- **Live sync.** Chats created, renamed or changed (approval mode, effort, skills) or discarded through the shared server (`themis call …`, another client) arrive as `thread-changed` events (`created|updated|removed`, metadata only) and update the open window's sidebar and shield without a reload; replays are harmless and the current selection is kept.
- Tasks "Earlier" summaries and the review toast show plain text: markdown is flattened (display-only, capped, not a sanitizer) and the toast uses the stored automation name, "(by agent)" tag and a friendly time instead of the raw timestamped title. Inline code in progress notes keeps its normal text colour.
- Shell and git approvals carry the whole command as structured `command` (`argv`, `cwd`, `background`); the approval box renders it as chips and never shows the joined summary for them. Only letters, numbers, punctuation and symbols are shown literally in a chip; anything else (controls, bidi, zero-width, combining marks, variation selectors, blank-looking letters such as U+3164 or U+2800, and the escape brackets themselves) becomes a highlighted `⟨U+XXXX⟩` escape, and a token with an escape is quoted. Digit shortcuts in the dialog start 500 ms after it opens and ignore key repeat.
