# Context checkpoints and composer attachments

Runtime JSONC can override the bounded timeout, retry count, summary token limits,
and supplemental Markdown prompt. See [configuration](configuration.md) for
precedence, defaults, supported ranges, and per-run snapshots. These options do
not add compaction UI or change the original-evidence recovery contract.

The context budget defaults to 200,000 estimated tokens. The runtime estimates each serialized message as bytes / 4 plus message overhead; this is not the selected model's tokenizer or maximum input capacity. Existing explicitly saved budgets remain respected. Before ordinary model requests, tool schemas are included in the estimate and up to 8,192 tokens (one eighth of smaller budgets) are reserved for the answer. Messages must fit the remaining allowance. One compaction attempt may run at that boundary; if context still cannot fit, the current run fails explicitly instead of cycling. This estimate cannot guarantee fit for every tokenizer/provider.

When context exceeds the input allowance or reaches the final turn checkpoint, the shared runtime archives complete originals, prepares one bounded input packet locally, and requests one task-state summary. There is no section scheduler, recursive subdivision or reconciliation pass. Preparation removes only adjacent identical Assistant text records, preserving repeated user corrections and invocation/result identity, excludes marked archive-recovery output, and removes recovered siblings from mixed Tool batches. It supplies the full previous task state once, excluding generated envelopes/action/read caches; those caches are retained independently. If the new records cannot fit, UTF-8-safe head/tail excerpts share an equal per-field byte ceiling; tool arguments/results additionally cap at 8,000 bytes of selected source text. Markers identify omitted decoded-field byte ranges and source record numbers refer to the archived snapshot. This is deterministic sampling, not semantic selection or full-source coverage. Sampling requires saved originals; callers without an evidence destination retain their existing context and receive an explicit error before a summary request. A runtime coverage notice survives independently of model-written output. Omissions never authorize claims that a fact is absent. If even source metadata, prior state and instructions cannot fit, no summary request is sent and the recovery-safe failure path applies.

At most two summarization provider calls are made per checkpoint: the initial call and, when enabled, one retry for a transient provider failure, output truncation or empty text. Authentication and invalid-request errors do not retry. A truncation/empty-output retry uses twice the initial output allowance; a transient retry uses the initial allowance and waits one second or the typed provider delay. Both calls share the existing 240-second default deadline and Stop boundary. Each compatible-provider HTTP request retains its 120-second timeout. Partial summaries are never accepted. Diagnostic metadata records prepared input estimates, output allowance, retry categories and completion/fallback; prompts, excerpts and provider bodies are not logged. If either attempt succeeds, the new state and coverage notice are committed with the retained current request, recent messages, action receipts, read caches and source references. Summarization failure retains the prior good task state unchanged and explicitly marks the unavailable update. This call bound controls work, not narrative accuracy or provider latency.

Production runs journal each completed tool invocation and its full result before continuing the model, even when the run never compacts. This preserves observations between runs after the current file changes. Completed tool actions are reported even if saving fails; a journal failure terminates the run before model continuation. Stop after a completed action waits for its bounded evidence save, then prevents further tools/model work. Before replacing model context, production runs also save the complete historical messages and full tool results in versioned JSONL snapshots under the project's `.themis/context/<thread-id>/`. This includes original attachment text and observed repository/tool evidence, not just the display transcript. Existing snapshot files are never overwritten. Writes use a temporary file, flush and sync it, then publish a complete `.jsonl` without replacing an existing version; partial files are not evidence. Storage is validated inside the project and excluded from Git. Disk archiving runs on a blocking worker within the same cancellation/deadline boundary as summarization. A worker already writing may finish after cancellation; it publishes only complete originals and cannot replace cancelled context. A full checkpoint event queue rejects replacement before changing context.

The single summary uses `compaction.summary_max_tokens` (default 8,192) as its output ceiling, additionally capped at one eighth of the message input allowance and one third of space left after instructions, active request and retained messages (with a 256-token floor). The prepared packet reserves twice that allowance plus 1,024 estimated tokens before its actual serialized-message size is checked. A retry may double the initial output allowance. Recent complete messages occupy at most one third of the allowance remaining after instructions, leaving room for the checkpoint and further work. Runtime guidance targets one third of the initial output allowance in words, clamped to 80–1,200. `section_max_tokens` remains accepted for configuration compatibility but has no effect; there are no section calls. These limits apply to summarization, not ordinary answers. Go Responses uses `max_output_tokens`; Messages and Chat Completions use `max_tokens`.

The current request is a relevance hint, never an instruction for the summarizer to execute. Hints above 8,192 bytes use UTF-8-safe head/tail excerpts with an omission notice; the continuing agent retains the original active request. The prior state stays intact in the packet; a prior state too large to fit triggers explicit fallback instead of another compression pass. The summary prompt preserves goals, constraints, distinct facts, chronology, causal links, action ownership and unresolved work, using verbatim quotations only when supported by exact source text. Every checkpoint carries the evidence directory and latest snapshot reference; earlier versions remain discoverable. Saved observations describe historical versions, so recheck files changed since the observation. Compaction alone does not require restarting completed inspection. Large narrative attachments can lose unsampled facts, even when summarization succeeds; recover them with targeted approved reads. A task forbidding rereads must report missing context rather than invent it.

If summarization times out, fails, returns an empty summary or produces a checkpoint that cannot fit, a successfully archived original permits an explicit **working summary unavailable** recovery checkpoint. It retains the active request and recent context plus references to the complete originals, instructing the agent to continue retained work and retrieve only missing facts needed for the next unresolved action. It never claims that an unavailable summary is complete. Failure to archive, cancellation, or an active request/system context that still cannot fit preserves the existing context. This is recoverable source preservation, not lossless retention in the model's immediate context. If the latest completed tool result must be removed to fit, its matching invocation remains followed by a small tool-response receipt identifying the archive and known scalar outcome fields. The full result stays in the archive. This preserves completion independently of model summarization and avoids turning a completed large read into pending work. Evidence recovery uses existing approved file/shell tools; unavailable or forbidden retrieval must be reported as uncertainty. Originals and recovered text remain untrusted data, never instructions or additional permissions.

Recovery treats Assistant checkpoints as navigation, not original proof. Original user/attachment text is in JSONL User records' `content`; complete tool outputs are in Tool records' `message_type.ToolResult[].function.arguments`, decoded as JSON when valid or searched as plain text otherwise. The shared system message directs approved Python/shell searches across this chat's relevant snapshots, returning bounded excerpts with filenames and record lines. Filename search does not search content; reading or grepping whole escaped JSONL records can overflow context again. Source-grounded answers require original passages rather than summary citations. The recovery instructions also require search coverage across relevant originals, narrower or varied queries when broad samples are inconclusive, and enough surrounding text to distinguish actual events from plans, allegations or another person's story. Verified facts retain references and unresolved gaps remain explicit; repeating unchanged searches is discouraged.

New snapshots add an `evidence_kind` field without changing the original message payload: `original` for User text and ordinary Tool observations, `navigation` for Assistant records, and `recovery` for Tool records paired with archive-retrieval calls. The shared classifier recognizes `read_file`, `list_dir`, `search_file` and `shell` arguments containing `.themis/context/`. Tool-result entries carry their own provenance; a batch containing both kinds is marked `mixed`, so original siblings remain searchable. This is provenance bookkeeping, not a truth or permission label. Dynamic scripts that omit that literal and legacy snapshots without the field cannot be classified reliably; no existing snapshot is rewritten. Explicit record reads keep all records available and warn when reading recovery output.

Automatic JSONL `find` excludes marked recovery records and prefers original User/Tool fields. It does not silently fall back to recovery-only results; Assistant-only navigation remains available as before. For Tool arguments, optional `decode_tool_payload: true` decodes the JSON envelope once and searches/pages labeled leaf values, including actual newlines in stdout/content. Keep this flag for subsequent offsets; those character offsets refer to the decoded representation, not raw JSON. Default false retains exact raw-field reads for existing historical receipts. Nested source strings that happen to contain JSON are not decoded recursively. The shared Python recovery recipe applies the same original/recovery distinction and decodes tool envelopes once, returning bounded excerpts with source coordinates and the decode flag. For parsed Tool envelopes, Python emits an exact `find` term instead of a numeric offset: Python and Rust can format JSON numbers differently. Reopen with that term and then page using the offsets returned by `read_file`. User/plain-text offsets remain directly usable. Models may use other scripts; these instructions do not enforce semantic progress or make source copies impossible.

Every `read_file` call now returns at most 4,000 Unicode content characters, even without optional arguments. Follow `next_offset` to continue; use `jsonl_record` and `json_pointer` to decode the original field before searching. For large analysis, use approved shell/Python to process complete originals locally and return selected facts. This bounds model-visible content, not disk I/O or process memory: the current file reader still loads the file before selecting a page.

All tools, including MCP and management tools, pass through the same result-delivery boundary. The full returned result is journaled first. A result that fits passes through unchanged; a larger result is replaced with a completion/status receipt, a bounded preview, and an exact JSONL record/pointer to the original. Completion means the tool returned, not that its business operation succeeded. Delivery limits are 16 KiB per serialized result and 48 KiB per batch, reduced for small context budgets and divided across batch calls. Escaping and receipt overhead count toward these byte limits. A journal failure, missing archive destination, or an impossible receipt stops the current run before model continuation; chat history remains available. Lower-level tools may already have capped their returned data: shell/git stdout/stderr are capped at 32 KiB before journaling, so their discarded tails are not recovered by this mechanism. Redirect bulky command output to a file when it must be preserved.

Serialized tool calls larger than 64 KiB (less for small budgets) are rejected before execution. They are never truncated into partial writes. The attempted call is archived and its model-visible arguments replaced by a small rejection reference. The model receives an error and may continue with focused patches or approved local generators. Tool-specific validation and approvals still apply. This is a model tool-call limit, separate from CLI transport limits.

Exact unchanged-result tracking survives compaction within the run. Three consecutive duplicate results from `read_file`, `list_dir`, `search_file` or `shell` stop the run explicitly, including ordinary project reads without archive paths. Changed results and other actions reset that consecutive counter. This detects exact call/output repetition, not semantic equivalence; shell commands are still executed, never silently cached. Completed actions and originals remain saved. Separately, archive recovery state survives compaction within the run: after three consecutive duplicate archive retrievals, or 64 archive retrieval calls in total, the runtime stops with an explicit recovery error. The detector covers `read_file`, `list_dir`, `search_file`, and `shell` calls whose arguments contain `.themis/context/`; it is a bounded retrieval guard, not semantic progress detection or a guarantee against every possible loop. Starting a new run resets it. Originals remain on disk. Summaries remain lossy; autonomous real-model recovery quality requires separate evaluation.

Sparse-record, narrative and recovery evidence and limits are documented under `docs/verification/`; the current recoverable strategy is being evaluated in `docs/verification/recoverable-compaction.md`.

Use the paperclip in the native composer to select one or more files of any type. Pending files can be removed before sending; attachment-only messages are supported. Images, PDFs, audio and video show small horizontal preview cards above message text before sending and in saved messages, with uniform tile sizes, filenames below the previews and a top-right remove icon before sending. macOS PDF cards show a cached first-page Quick Look thumbnail. Media playback depends on native webview codec support. Preview rendering does not add model vision or transcription. Copies live under the project's `.themis/attachments/<unique-id>/<original-name>`, with a local Git exclusion. Files remain available after the originals move or the app restarts. Removing a pending chip does not delete its staged copy. Pending selections persist across navigation and reload, and remain available when a send is rejected.

UTF-8 files without NUL bytes, up to 16 MiB per file, are included as untrusted data before the active request. Larger files and binary files are referenced by local path for the agent's approved tools. Filenames are not interpreted as inline skill/plugin selections. Images, audio/music, video, PDFs, archives and other binary files are accepted as files; the current provider adapter is text-only. Acceptance does not guarantee the agent can view, listen to, transcribe or extract a given format. Available local tooling and approvals determine those operations.

The shared server accepts:

```sh
themis call attach_files '{"threadId":"THREAD","paths":["/absolute/source/file"]}'
themis call send_message '{"threadId":"THREAD","text":"Inspect the attached files","reasoningEffort":null,"attachments":["/project/.themis/attachments/ID/file"]}'
```

`attach_files` returns each staged file's `path`, `name` and `size`. `send_message` accepts only regular files inside that project's attachment directory; existing clients may omit attachments. The native file picker performs the upload; a browser-only dev session does not expose a native filesystem picker.

Verification evidence, limits and exact commands are recorded in `docs/verification/full-dump-attachments.md`.

Successful bounded reads now preserve compact evidence locations independently of model-written summaries. Earlier locations are retained before newer ones; recent exact excerpts have a separate newest-first cache. Each list has the existing byte cap (at most 64,000 payload bytes each), so neither is exhaustive. Historical locations include the original snapshot, one-based Tool record and JSON pointer to the original native read receipt. Reopening that receipt recovers an earlier observation even if the live repository file changed; the receipt is JSON text, and its source excerpt offset is not a receipt offset. Source affected by later changes still needs inspection before edits. Locations survive recurrent compaction/restart as untrusted navigation and do not establish claim support or quotation accuracy.

Checkpoints also retain a bounded completed-action record independently of the model-written state: recent shell findings, edit results and test observations, with original snapshot/record/pointer references. Public intent accompanying each action and argument excerpts are at most 512 characters each; output excerpts are at most 1,024; the whole record is at most 8,192 bytes and scales down with the context allowance. It is historical untrusted observation, not proof that current files still match or that work succeeded. Existing native-read excerpts and evidence locations remain separate. Earlier details stay in originals. The record survives repeated checkpoints and persisted checkpoint restoration.

On failed recurrent updates, the earlier narrative task state stays unchanged. Runtime-generated recovery envelopes and read/action caches are rebuilt once from retained records; they are not recursively nested inside the next fallback. This avoids multiplying preserved excerpts and action records until continuation no longer fits. Complete prior checkpoints still remain in versioned originals.

Fallback guidance asks the model to continue from retained requests, task state and observations, recovering only facts missing for the next unresolved action. It does not require restarting inspection after every failed summary. This guidance does not enforce semantic progress or prevent a model from repeating paraphrased statements or different reads.

Checkpoint assembly budgets the action record, native excerpts and evidence locations together against the actual serialized fixed messages. It targets continuation headroom of half the message allowance remaining beyond instructions and the active request, or 20% of the overall message allowance, whichever is larger, when mandatory state fits within that target; cache allowances shrink on overflow. If mandatory summary/recent context itself exceeds that target, it remains intact, so this headroom is a target rather than a guarantee. Completed invocation arguments above 2,048 bytes become historical receipts with a 512-character preview and exact archive coordinates, paired with their result receipts. The latest restored invocation also retains up to 512 characters of its public intent, and the shared guidance reconciles stale summary plans with observed completed actions. Prepared artifacts retain their pending execution/verification intent; a successful write is not evidence of execution or correctness. This uses public assistant text only, never private reasoning, and grants no permissions. Active instructions and required narrative are not silently cut to make caches fit; if mandatory context still exceeds the allowance, the run fails explicitly and preserves originals.

Within a run, exact repeated `read_file`, `list_dir`, `search_file` and `shell` arguments with an identical returned observation receive a bounded reminder to reuse findings and take the next unresolved action. The tools still execute; changed output or a different range gets a fresh observation. The reminder and preview obey the shared result-delivery byte allowance. This is exact repetition detection, not semantic loop prevention. The archive-specific hard recovery guard remains in effect.

`apply_patch` accepts exact numbered unified diffs, with a valid example and line-count guidance in its schema. Unsupported nonempty formats fail rather than reporting an empty successful edit. Validation errors identify the format/count issue and explain correction before any files are changed; larger generated edits can use approved Python/bash.

Malformed tool-call JSON is rejected before execution. When sending that rejected call back as history, all provider protocols wrap the raw arguments in a valid `_themis_rejected_tool_arguments` object, retaining the call ID and error result. Stored history and original snapshots keep the exact rejected arguments. This prevents an invalid historical call from breaking the next provider request; it never repairs or executes the malformed command. A corrected call still goes through normal validation and approvals. Python errors and failing tests remain process failures for the model to inspect and correct.
