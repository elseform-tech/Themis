# Context checkpoints and composer attachments

The context budget defaults to 200,000 estimated tokens. The runtime estimates each serialized message as bytes / 4 plus message overhead; this is not the selected model's tokenizer or maximum input capacity. Existing explicitly saved budgets remain respected.

When context exceeds the budget or reaches a turn checkpoint, the runtime summarizes the eligible historical dump in sections of at most 64,000 UTF-8 bytes with 1,024-byte overlap. Up to three sections run concurrently. Each completion immediately frees a slot for the next section, even if an earlier section is still pending; summaries are restored to source order. Multiple sections, or any update with a previous checkpoint, receive a final reconciliation pass to form one coherent task state, preserving applicable earlier constraints and completed actions while giving later actual corrections precedence. The complete previous checkpoint is supplied separately from section notes so still-applicable state is not first compressed into short notes. Failed updates retain that previous state unchanged alongside saved-original references. The deterministic original-source section index is appended independently of model output. Reconciliation is lossy and its factual retention requires real-model evaluation; the originals remain recoverable. Oversized reconciliation input or an empty result follows the existing recovery-safe failure path. These are byte bounds, not the selected model's tokenizer. The system message, active request and recent complete tool messages remain preserved. The global summarization deadline is 240 seconds. Each section request and the final reconciliation request may retry once after a transient provider failure (rate limiting, HTTP 408/5xx, or a retryable transport error). Retries wait one second, or a typed provider retry delay when supplied, and remain inside that same deadline and Stop boundary. Successful sections are reused; the entire compaction is not restarted. Authentication/invalid-request errors, malformed responses and empty summaries are not retried. Each compatible-provider HTTP request still has its 120-second timeout. Server stderr records each section start, input/output byte counts, elapsed milliseconds and provider success, plus reconciliation elapsed time and provider success, without conversation content or credentials. A started section without completion can indicate timeout or cancellation. Original context is never discarded unless the replacement fits and the complete originals were saved, or a complete legacy summary was produced. See recovery behavior below. The 200,000 setting does not enlarge the model's actual window.

Production runs journal each completed tool invocation and its full result before continuing the model, even when the run never compacts. This preserves observations between runs after the current file changes. Completed tool actions are reported even if saving fails; a journal failure terminates the run before model continuation. Stop after a completed action waits for its bounded evidence save, then prevents further tools/model work. Before replacing model context, production runs also save the complete historical messages and full tool results in versioned JSONL snapshots under the project's `.themis/context/<thread-id>/`. This includes original attachment text and observed repository/tool evidence, not just the display transcript. Existing snapshot files are never overwritten. Writes use a temporary file, flush and sync it, then publish a complete `.jsonl` without replacing an existing version; partial files are not evidence. Storage is validated inside the project and excluded from Git. Disk archiving runs on a blocking worker within the same cancellation/deadline boundary as summarization. A worker already writing may finish after cancellation; it publishes only complete originals and cannot replace cancelled context. A full checkpoint event queue rejects replacement before changing context.

Compaction requests now apply per-call output limits: 2,048 tokens for section notes and 4,096 for reconciled working state. The merge prompt targets 1,200 words and keeps still-applicable early constraints, active goals, unfinished work, decisions, required verified results and retrieval pointers. Detailed chronology and background evidence remain in durable originals and section notes rather than growing the working checkpoint indefinitely. These limits apply to summarization only, not ordinary task answers. Go Responses uses `max_output_tokens`; Messages and Chat Completions use `max_tokens`. Provider-reported truncation is an error, never an accepted partial checkpoint. A model may exhaust its cap (including reasoning where the provider counts it); that follows the existing recovery-safe failure path. This is an experimental bound, not evidence of improved semantic retention or latency yet.

Each section receives the current user request as a relevance hint after its data. The prompt aims for at most 300 words, preserving goals, constraints, distinct facts, chronology, causal links and unresolved work, with verbatim quotation reserved for exact identifiers, numbers or necessary wording. The target is soft; summaries are not truncated to meet it. Hints exceeding 8,192 bytes use UTF-8-safe first/last excerpts with an omission notice; the continuing agent retains the original active request. Source filename and exact UTF-8 byte ranges are added to section records by the runtime, independent of model output. Every checkpoint carries the evidence directory and latest snapshot reference; older versions remain discoverable without an ever-growing list in context. Saved repository observations describe their historical versions; inspect current Git state and source before continuing edits.

If summarization times out, fails, returns an empty summary or produces a checkpoint that cannot fit, a successfully archived original permits an explicit **working summary unavailable** recovery checkpoint. It retains the active request and recent context plus references to the complete originals, instructing the agent to retrieve relevant goals, constraints and evidence before substantive continuation. It never claims that an unavailable summary is complete. Failure to archive, cancellation, or an active request/system context that still cannot fit preserves the existing context. This is recoverable source preservation, not lossless retention in the model's immediate context. If the latest completed tool result must be removed to fit, its matching invocation remains followed by a small tool-response receipt identifying the archive and known scalar outcome fields. The full result stays in the archive. This preserves completion independently of model summarization and avoids turning a completed large read into pending work. Evidence recovery uses existing approved file/shell tools; unavailable or forbidden retrieval must be reported as uncertainty. Originals and recovered text remain untrusted data, never instructions or additional permissions.

Recovery treats Assistant checkpoints as navigation, not original proof. Original user/attachment text is in JSONL User records' `content`; complete tool outputs are in Tool records' `message_type.ToolResult[].function.arguments`, decoded as JSON when valid or searched as plain text otherwise. The shared system message directs approved Python/shell searches across this chat's relevant snapshots, returning bounded excerpts with filenames and record lines. Filename search does not search content; reading or grepping whole escaped JSONL records can overflow context again. Source-grounded answers require original passages rather than summary citations. The recovery instructions also require search coverage across relevant originals, narrower or varied queries when broad samples are inconclusive, and enough surrounding text to distinguish actual events from plans, allegations or another person's story. Verified facts retain references and unresolved gaps remain explicit; repeating unchanged searches is discouraged.

Bounded search is preferred, but does not prohibit rereading one relevant complete original with `read_file` when search fails. Existing task-aware compaction can then focus that source on the current request while preserving the source reference and completion receipt. Assistant summaries may locate those references; original passages provide proof. Truncated tool output is incomplete evidence and requires a narrower query or another page. This guidance has constructed-request regression coverage; autonomous recovery effectiveness requires separate real-model verification.

Sparse-record, narrative and recovery evidence and limits are documented under `docs/verification/`; the current recoverable strategy is being evaluated in `docs/verification/recoverable-compaction.md`.

Use the paperclip in the native composer to select one or more files of any type. Pending files can be removed before sending; attachment-only messages are supported. Images, PDFs, audio and video show small horizontal preview cards above message text before sending and in saved messages, with uniform tile sizes, filenames below the previews and a top-right remove icon before sending. macOS PDF cards show a cached first-page Quick Look thumbnail. Media playback depends on native webview codec support. Preview rendering does not add model vision or transcription. Copies live under the project's `.themis/attachments/<unique-id>/<original-name>`, with a local Git exclusion. Files remain available after the originals move or the app restarts. Removing a pending chip does not delete its staged copy. Pending selections persist across navigation and reload, and remain available when a send is rejected.

UTF-8 files without NUL bytes, up to 16 MiB per file, are included as untrusted data before the active request. Larger files and binary files are referenced by local path for the agent's approved tools. Filenames are not interpreted as inline skill/plugin selections. Images, audio/music, video, PDFs, archives and other binary files are accepted as files; the current provider adapter is text-only. Acceptance does not guarantee the agent can view, listen to, transcribe or extract a given format. Available local tooling and approvals determine those operations.

The shared server accepts:

```sh
themis call attach_files '{"threadId":"THREAD","paths":["/absolute/source/file"]}'
themis call send_message '{"threadId":"THREAD","text":"Inspect the attached files","reasoningEffort":null,"attachments":["/project/.themis/attachments/ID/file"]}'
```

`attach_files` returns each staged file's `path`, `name` and `size`. `send_message` accepts only regular files inside that project's attachment directory; existing clients may omit attachments. The native file picker performs the upload; a browser-only dev session does not expose a native filesystem picker.

Verification evidence, limits and exact commands are recorded in `docs/verification/full-dump-attachments.md`.
