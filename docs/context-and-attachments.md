# Context checkpoints and composer attachments

Runtime JSONC can override the bounded timeout, retry count, summary token limits,
and supplemental Markdown prompt. See [configuration](configuration.md) for
precedence, defaults, supported ranges, and per-run snapshots. These options do
not add compaction UI or change the original-evidence recovery contract.

The context budget defaults to 200,000 estimated tokens and accepts 24,000, 200,000 and 256,000 with the same adaptive algorithm. It estimates serialized message bytes / 4 plus overhead, includes tool schemas, reserves the actual ordinary output limit (up to 8,192; one eighth of smaller budgets), and reserves a 2% safety margin with a 256-token floor. The selected provider capacity remains unverified unless independently established; configured budget is not proof of model support.

Before requests, maintenance starts at 83% of usable message space and semantic compaction at 93%, with a bounded adjustment for six projected interactions using observed growth. Maintenance snapshots exact originals and replaces only old completed tool arguments/results with receipts; it keeps the latest interaction, active request and unfinished exchanges. Receipts identify immutable originals and known outcome fields, not proof that a write was executed or tested. Archive size and reaching the last tool turn do not trigger a summary. Working context must still fit after one successful compaction, or the run stops explicitly.

Each checkpoint is one summary request. A fitting input is supplied whole; otherwise long fields are cut to an equal head/tail excerpt ceiling with UTF-8 byte coordinates, and if even empty fields do not fit, the oldest new records are left out. A coverage notice in the request says what was cut, and cutting requires saved originals: the omitted detail stays there for `recall`. Recovery output and prior generated checkpoint caches are excluded; previous task state remains a separate input. The request allows up to two automatic retries with exponential backoff and jitter; every attempt must pass structural validation, and retry output is capped at twice the initial allowance. Compaction has no user-facing retry command. Model quality is evaluated separately.

Attached documents keep the staged pipeline. Source packets are packed against the complete constructed summary request,
including escaped fragment wrappers, source coordinates, prompts and prior state.
The estimator reserves retry output and prompt margin before accepting a packet.
This avoids applying worst-case JSON escaping discounts twice to ordinary prose;
UTF-8 source ranges still cover every serialized eligible record exactly once.
It changes request packing, not the byte-based estimator's accuracy or the
configured model capacity. Live token and latency gains require measurement.
Saved stage identity binds the request, purpose, resolved summary model and
effective initial/retry output allowances. Completed compatible document capsules
remain reusable. Ambiguous older partial stage keys are preserved on disk rather
than reused under a guessed output allowance.

Ordinary answer requests allow up to 300 seconds per attempt, with at most three attempts under a 900-second overall deadline including backoff. Retry delays use one- then two-second exponential bases plus jitter up to half the base. Two failures that usually clear with time get more room inside the same deadline: a rate limit (HTTP 429) is retried up to five times after about 10, 20, 40, 80 and 160 seconds, and a cut-off (truncated) provider response up to four times, so a long run is not lost to a temporary limit. A longer `Retry-After` remains a minimum. Public text prevents retry, and completed tools are not replayed. A cut-off (output-limit) response before public text is published retries with the selected model and reasoning settings and a doubled output cap each time, up to four times the original and never above the model's own limit, because a thinking model's reasoning counts toward the cap; failed-attempt tool calls are discarded. A Responses stream cut off at its output limit counts as a cut-off. A stream that drops or fails part-way (ended before completion, failed or incomplete, a stream error event) is retried like a transport error before public text is published. Empty answers (no nonblank public text and no tool calls) cannot finish a run silently: they may retry within those same bounds before public output, each retry adding a runtime note that the last reply was empty, then fail explicitly if no usable answer arrives. Streaming requests that receive truncated JSON responses reject them before exposing partial text or executing calls.

Production runs journal each completed tool invocation and its full result before continuing the model, even when the run never compacts. This preserves observations between runs after the current file changes. Completed tool actions are reported even if saving fails; a journal failure terminates the run before model continuation. Stop after a completed action waits for its bounded evidence save, then prevents further tools/model work. Before replacing model context, production runs also save the complete historical messages and full tool results in versioned JSONL snapshots under the project's `.themis/context/<thread-id>/`. This includes attachment text actually admitted to context and observed repository/tool evidence, not just the display transcript. Complete staged attachment files remain separately available even when only their bounded maps were admitted. Existing snapshot files are never overwritten. Writes use a temporary file, flush and sync it, then publish a complete `.jsonl` without replacing an existing version; partial files are not evidence. Storage is validated inside the project and excluded from Git. Disk archiving runs on a blocking worker within the same cancellation/deadline boundary as summarization. A worker already writing may finish after cancellation; it publishes only complete originals and cannot replace cancelled context. A full checkpoint event queue rejects replacement before changing context.

Initial summary output uses the configured ceiling (8,192 tokens by default), scaled down against retained messages and continuation capacity. Retries may use up to twice the effective initial allowance, including after transient provider errors; the default initial ceiling can therefore permit a 16,384-token retry. Provider limits and reserved capacity still apply. For attached documents, source stage allowances also reserve the whole consolidation packet, including retry output. The legacy section_max_tokens field remains accepted without independently overriding this calculation. The overall summary job defaults to 900 seconds and can be configured up to 1800; explicit existing overrides are preserved. Each request is at most 300 seconds and is further allocated from the remaining shared deadline, reserving time for later stages and consolidation. Three attempts are a maximum, since waits and downstream reservations can shorten later attempts. Stop cancels requests/waits without replacing context.

The current request is a relevance hint, never an instruction for the summarizer to execute. The original active request is retained. The checkpoint prompt preserves goals, chronology, attribution, negation, confirmed effects, proposals versus decisions and unresolved actions. Exact quotes require original passages. State too large for the packet or final context causes an explicit suspended run, preserving originals and completed stage work. Current user instructions take precedence over historical quotations.

Required summarization is transactional: only a complete, nonempty, bounded provider result and successful checkpoint assembly can replace context. Timeout, empty/truncated output, provider error, invalid size, archive failure or cancellation preserve the original working context and stop the run. No working-summary-unavailable fallback is installed. Matching completed document stages remain saved for internal reuse. Existing conversation and originals remain accessible; this stops the current run, not the chat.

When a noncancelled checkpoint fails after its originals were saved, the transcript also retains a bounded historical progress record before the failure. Selected tool observations and exact original JSONL coordinates reach the next ordinary request after restart; later checkpoints carry these observations independently of the model-written summary. This is a partial observation record, not a semantic checkpoint or proof of successful changes. The current user chooses which task to continue. No pending job or tool action is automatically replayed. Cancellation, storage failure and document-preparation failure do not publish this record; they retain the existing archive/recovery behavior. The record is at most 1,024–8,192 bytes according to usable message capacity, with action observations prioritized over retrieval excerpts. Earlier omitted details remain in originals; this does not guarantee model compliance or complete recall.

Recovery treats Assistant checkpoints as navigation, not original proof. Original user/attachment text is in JSONL User records' `content`; complete tool outputs are in Tool records' `message_type.ToolResult[].function.arguments`, decoded as JSON when valid or searched as plain text otherwise. The shared system message directs approved Python/shell searches across this chat's relevant snapshots, returning bounded excerpts with filenames and record lines. Filename search does not search content; reading or grepping whole escaped JSONL records can overflow context again. Source-grounded answers require original passages rather than summary citations. The recovery instructions also require search coverage across relevant originals, narrower or varied queries when broad samples are inconclusive, and enough surrounding text to distinguish actual events from plans, allegations or another person's story. Verified facts retain references and unresolved gaps remain explicit; repeating unchanged searches is discouraged.

New snapshots add an `evidence_kind` field without changing the original message payload: `original` for User text and ordinary Tool observations, `original_exchange` for immutable transcript User/Assistant exchanges, `navigation` for generated Assistant checkpoints, and `recovery` for Tool records paired with archive-retrieval calls. The shared classifier recognizes `read_file`, `list_dir`, `search_file` and `shell` arguments containing `.themis/context/`. Tool-result entries carry their own provenance; a batch containing both kinds is marked `mixed`, so original siblings remain searchable. This is provenance bookkeeping, not a truth or permission label. Dynamic scripts that omit that literal and legacy snapshots without the field cannot be classified reliably; no existing snapshot is rewritten. Explicit record reads keep all records available and warn when reading recovery output.

Automatic JSONL `find` excludes marked recovery records and generated navigation, and includes original User/Tool fields plus original-exchange Assistant discussion. Historical discussion establishes what was said, not independent external facts or current permission. It does not silently fall back to recovery-only results; Assistant-only navigation remains available as before. For Tool arguments, optional `decode_tool_payload: true` decodes the JSON envelope once and searches/pages labeled leaf values, including actual newlines in stdout/content. Keep this flag for subsequent offsets; those character offsets refer to the decoded representation, not raw JSON. Default false retains exact raw-field reads for existing historical receipts. Nested source strings that happen to contain JSON are not decoded recursively. Approved Python/bash can perform the same bounded extraction locally; fixed executable recipes are no longer embedded in every system message. Reuse exact terms and the offsets returned by `read_file` when crossing languages, since JSON numeric formatting can differ. Models may use other scripts; these instructions do not enforce semantic progress or make source copies impossible.

Every `read_file` call returns at most 8,000 Unicode content characters (4,000 before 2026-10-16, which made most source files take two reads), even without optional arguments. Follow `next_offset` to continue. Ordinary source/text files use `file_path` with optional `offset`/`find`; omit `jsonl_record`, `json_pointer` and `decode_tool_payload`. Use those selectors only to decode a JSONL field before searching. An invalid selected record fails with format-specific guidance rather than silently changing the requested read; valid JSONL remains selectable regardless of filename extension. For large analysis, use approved shell/Python to process complete originals locally and return selected facts. This bounds model-visible content, not disk I/O or process memory: the current file reader still loads the file before selecting a page.

Successful JSONL selections include a SHA-256 of the complete authorized source before field selection or decoding. Summary preparation retains validated bounded excerpts of original User/Tool records and historical original exchanges read through `read_file`, even when optional read caches have no space. These are labeled `original_derived_excerpt`, with source path/hash, record, pointer, raw/decoded mode and Unicode character range. They remain secondary observations, not independent evidence or current instructions. Identical source coordinates are deduplicated; different records, fields, modes and source versions remain distinct. Recursive recovery copies and generated navigation remain excluded. Archives and their search classifications are unchanged. Both fitting and staged summaries use this projection; this does not guarantee factual retention in the model-written summary.

When such a read envelope exceeds serialized delivery limits, the complete observed envelope is saved first. Delivery then shortens its content when provenance and a nonempty excerpt fit, keeping normal pagination consistent; search excerpts start at the actual match and must fit the complete needle. If that minimum cannot fit, existing offloading remains in effect. No extra file read or permission bypass occurs during summary preparation. Original batch result indices remain intact in prepared inputs, so their JSON pointers still address the saved originals.

Reversible maintenance preserves validated original-derived read pairs and all delivered ordinary tool observations until semantic compaction can consume them. Results that a successful checkpoint has already summarized (including retained recent messages and history restored from a checkpoint) may become receipts; only this run's newer observations stay protected. This includes plain-file reads, selected shell output and MCP results; an unmatched result stays protected because its provenance is unknown. Known recursive or invalid archive recovery copies remain reducible. Retained recent original-derived reads keep the selectors required for validation. Completed invocation arguments can still be offloaded: strict non-executable receipts preserve their pre-offload recovery classification, so an archive pointer does not turn a surviving ordinary result into excluded recovery at the next checkpoint. Malformed or legacy receipt shapes use the conservative existing classifier. These labels do not grant permission or establish truth. Protected observations can require semantic compaction sooner than receipts, but maintenance must not erase acquired evidence before it reaches the summarizer. It plans reductions before saving: protected-only passes and known no-op/expanding mixed batches publish no redundant full snapshot. Public-intent excerpts, including their location notes, stay within the maintenance bound even under long evidence paths.

All tools, including MCP and management tools, pass through the same result-delivery boundary. The full returned result is journaled first. A result that fits passes through unchanged; a larger result is replaced with a completion/status receipt, a bounded preview, and an exact JSONL record/pointer to the original. Completion means the tool returned, not that its business operation succeeded. Delivery limits are 16 KiB per serialized result and 48 KiB per batch, reduced for small context budgets and divided across batch calls. When a batch has more calls than can each get 1 KiB, the first calls that fit run and the rest return unexecuted with a `Not run:` note asking for a smaller batch, so the run continues; only a budget too small for even one call stops it. Escaping and receipt overhead count toward these byte limits. A journal failure, missing archive destination, or an impossible receipt stops the current run before model continuation; chat history remains available. Lower-level tools may already have capped their returned data: shell/git stdout/stderr are capped at 32 KiB before journaling, so their discarded tails are not recovered by this mechanism. Redirect bulky command output to a file when it must be preserved.

Serialized tool calls larger than 64 KiB (less for small budgets) are rejected before execution. They are never truncated into partial writes. The attempted call is archived and its model-visible arguments replaced by a small rejection reference. The model receives an error and may continue with focused patches or approved local generators. Tool-specific validation and approvals still apply. This is a model tool-call limit, separate from CLI transport limits.

Unchanged-result tracking survives compaction within the run. Every time three consecutive observations already seen from `read_file`, `list_dir` or `search_file` occur in a run, the third result carries a `loop_warning` (keep what is needed in notes or output if an earlier read was summarised away, otherwise take the next unfinished step), also when alternating between files outside archive paths. Repeats never stop a run: a re-read after a checkpoint can be necessary, and stopping hides why the agent repeats itself. The run's turn limit bounds a real loop (the run ends incomplete with a handoff summary), and the long-horizon eval counts the warnings per run. Canonical native read output identifies the path, range and content, so `source.txt` and `./source.txt` share an observation. A repeated result that is byte-identical to a result still present in context is delivered as a short freshness receipt (`repeated_unchanged`, `unchanged_since_call` and the read coordinates) instead of being resent; when the earlier copy has been compacted or offloaded, the full result is returned with a reminder. A novel observation resets the duplicate streak; action tools clear the native observation history. Shell may mutate files without output, so it clears native read history and retains only the existing consecutive identical-call/output check. All calls still execute and are journaled before detection; none are silently cached. This detects exact observations, not semantic equivalence or filesystem progress. Completed actions and originals remain saved. Separately, archive recovery is capped at 64 retrieval calls per run (`read_file`, `list_dir`, `search_file` and `shell` calls whose arguments contain `.themis/context/`); repeated identical archive reads get the same warnings. It is a bounded retrieval guard, not semantic progress detection or a guarantee against every possible loop. Starting a new run resets it. Originals remain on disk. Summaries remain lossy; autonomous real-model recovery quality requires separate evaluation.

Before each bounded model request the runtime emits a `context_budget` event with byte-estimated counts only: the budget, usable message tokens, used tokens, tool-definition, reply and safety reserves, the maintenance and auto-compact thresholds, whether the observed growth projects a checkpoint within about two interactions (`compaction_soon`), and a breakdown into system, checkpoint, attachments, conversation and tool activity. It never carries message content. When a turn triggers a context checkpoint, one more `context_budget` with that turn's input already counted is emitted just before `context_compacting`, so the checkpoint divider reads the size that triggered it ("Context compacted · 99% → 57%") rather than the previous turn's size. The composer's context meter and heads-up use it; it is stored with other run events. Optional fields add the uncorrected estimate (`raw_estimated_tokens`), the previous request's provider-reported input tokens (`provider_input_tokens`) and the correction ratio in thousandths (`calibration_ratio_milli`); they are absent before the first usage report and from older stored events.

### Estimate calibration and overflow recovery

The byte-based estimate is corrected per run by what the provider reports. After each ordinary model request that returns input (prompt) tokens, the runtime computes `reported / (estimated messages + tool definitions)`, clamps it to 0.75-4.0 and smooths it (the first observation sets the ratio; later ones average 50/50 with it). Maintenance, the semantic-compaction trigger, the growth forecast, the hard "still exceeds the request budget" check, the end-of-run handoff fit check and the `context_budget` event all use the calibrated estimate. Compaction itself receives the equivalent raw budget (refreshed before every compaction, floored at 256 tokens or an eighth of the budget so heavy tool schemas cannot collapse it to zero), so its splits and fit checks stay consistent. Without provider usage (or with zero tokens) nothing changes: the ratio stays absent and behavior is identical to the raw estimate. The ratio lives only in the run; nothing but numbers is captured, and summarization requests never update it.

Per request, a content-free `token_calibration` sample (`raw_estimated_input_tokens`, `calibrated_estimated_input_tokens`, `provider_input_tokens`, `observed_ratio`, `calibration_ratio`, `raw_error`, `calibrated_error`) is written to diagnostics and to the run's context metrics (`token_calibration`, last 32). The calibrated value is the estimate used for that request, before it was updated by its own report.

A provider error that conservatively indicates context length exceeded (HTTP 400, 413 or 422 with the OpenAI-compatible `context_length_exceeded` code or a well-known message such as "maximum context length", "prompt is too long", Anthropic `request_too_large` or Gemini "input token count ... exceeds the maximum number of tokens"; 429 is never classified) is recovered once per request, before any answer text: the ratio is raised so the request counts as over budget, one compaction runs, and the request is retried. A second consecutive overflow fails the run explicitly with originals preserved. Completed tools are never replayed, and the retry does not consume a turn. Other 4xx errors are not classified as overflow and keep their normal handling.

Estimation caches each message's size by content, and checkpoint split selection is linear in the message count; neither changes any result.


## The `recall` tool

Older details are not in a checkpoint summary. Every production run offers one read-only built-in tool, `recall`, that searches this chat's saved originals: the versioned `snapshot-*.jsonl` files and exported `history-source-*.jsonl` exchanges under `.themis/context/<thread>/`, and the attachment originals the chat referenced (UTF-8 files up to 64 MiB). The per-request system text carries only a short pointer: a checkpoint is a lossy paraphrase, not a source; before stating exact wording, numbers, names or quotes that are not verbatim in context, call `recall` with 2-5 distinctive keywords (not the whole question), try other keywords or `around` on a miss, answer only from what it returns and cite its coordinates. Each checkpoint repeats only the directory, snapshot count and latest snapshot with a one-line pointer. The former JSONL/Python recovery recipe is no longer in the shared system text; `read_file`'s `jsonl_record`, `json_pointer`, `offset`, `find` and `decode_tool_payload` selectors still work but are not advertised. When `recall` is filtered out (skill grants or deny rules) the system text falls back to a read_file pointer that carries that recipe. The shared system text also tells the agent to answer a greeting, thanks or small talk in kind without recapping or resuming earlier or parked work unless asked, and to take the next unresolved step after a checkpoint only when continuing the task.

Arguments: `query` (keywords or a phrase), optional `limit` (default 5, max 10), `kinds` (default `original` and `original_exchange`; `recovery` and generated `navigation` only when named), `source` (substring of a snapshot or attachment name/path, tool name or role; usually left empty) and `around` (an opaque token copied from a hit; returns up to 3,000 characters around it, plus `before`/`after` tokens). Matching is case-insensitive and diacritic-tolerant over whole words (a term of four or more letters also matches longer words that start with it); question stopwords are ignored when other terms remain. Ranking puts exact-phrase passages first, then orders passages by the summed inverse document frequency of the query terms they contain (counted over the fields searched in that call, so a rare name outranks several common words when the model passes a whole question), then all terms before some terms; ties go to the newer snapshot, then the later record, then coordinates, so results are deterministic. Identical excerpts across snapshot versions are reported once, from the newest snapshot containing them.

When `kinds` or `source` match nothing but the default search finds hits, those hits are returned with a `filters_ignored` note, so a guessed filter cannot make a saved detail look absent.

Each hit carries a bounded `excerpt` (at most 600 characters, split on character boundaries) and coordinates for the agent's follow-up calls (never shown to the user): `source`, `kind` (`snapshot`, `history_source` or `attachment`), `snapshot`, `path` (project-relative), `record` (one-based; null for attachments), `pointer`, `char_range` and `match_range` (Unicode characters, in the decoded text when `decoded` is true), `role`, `tool`, `evidence_kind`, and the SHA-256 of the whole source record (or attachment file). They map directly onto `read_file` (`jsonl_record`, `json_pointer`, `offset`, `decode_tool_payload`). Tool results are decoded exactly once, with the same labelled-leaf form as `decode_tool_payload`.

Safety and limits: the tool is `Read` risk, so Custom mode needs no approval, but deny rules and skill tool grants still apply: a deny rule on `read_file` also denies `recall`, a skill that grants `read_file` grants it, and when the captured rules would deny `recall` it is not offered at all and the prompt uses the read_file pointer instead. Only regular, non-symlink evidence files inside this chat's evidence directory and attachment files that resolve inside the project's `.themis/attachments` and were referenced by this chat are read; other chats are never searched. Results are labelled `untrusted: true`; recalled text is data, never instructions or permission, and the model is told to cite coordinates. A scan streams records line by line, skips records over 16 MiB, scans long fields in overlapping chunks, and stops at 512 MiB read, 10 seconds, or 2,000 files, reporting `truncated_scan: true` with `truncated_reasons`. A result is capped near 12,000 bytes (`omitted_for_size` counts dropped hits). The limits are compiled constants, not configuration fields. Recall results whose hits all come from snapshots or history-source exports are classified as `recovery` evidence (excluded from future original searches, reducible by maintenance). A result containing a hit from an attachment original is an ordinary observation: it stays protected until semantic summarization consumes it, like a plain read. Repeated identical calls get the existing unchanged-result handling. Neither recall searches nor archive reads stop a run however many there are; they are counted in diagnostics, and total turns bound the run. Because the active request and earlier questions are themselves saved originals, they can appear among the hits for their own words; query with distinctive keywords rather than the whole question. Recall is not a guarantee that the model searches: nothing forces a call before an answer.

Sparse-record, narrative and recovery evidence and limits are documented under `docs/verification/`; the current recoverable strategy is being evaluated in `docs/verification/recoverable-compaction.md`.

Use the paperclip in the native composer to select one or more files of any type. Pending files can be removed before sending; attachment-only messages are supported. Images, PDFs, audio and video show small horizontal preview cards above message text before sending and in saved messages, with uniform tile sizes, filenames below the previews and a top-right remove icon before sending. macOS PDF cards show a cached first-page Quick Look thumbnail. Media playback depends on native webview codec support. Preview rendering does not add model vision or transcription. Copies live under the project's `.themis/attachments/<unique-id>/<original-name>`, with a local Git exclusion. Files remain available after the originals move or the app restarts. Removing a pending chip does not delete its staged copy. Pending selections persist across navigation and reload, and remain available when a send is rejected.

Small UTF-8 files without NUL bytes are admitted within one aggregate attachment allowance: at most 64 KiB, further capped at half the configured token-budget number in bytes. Larger files receive bounded heading maps with byte/line coordinates, size and explicit incomplete-coverage notices. A map is not a semantic summary. Original copies stay available for approved local tools. Full retelling requires full source processing, rather than assuming a sampled map is complete. Binary/media acceptance does not add model vision, audio or extraction capabilities.

The shared server accepts:

```sh
themis call attach_files '{"threadId":"THREAD","paths":["/absolute/source/file"]}'
themis call send_message '{"threadId":"THREAD","text":"Inspect the attached files","reasoningEffort":null,"attachments":["/project/.themis/attachments/ID/file"]}'
```

`attach_files` returns each staged file's `path`, `name` and `size`. `send_message` accepts only regular files inside that project's attachment directory; existing clients may omit attachments. The native file picker performs the upload; a browser-only dev session does not expose a native filesystem picker.

Verification evidence, limits and exact commands are recorded in `docs/verification/full-dump-attachments.md`.

Runs that save evidence offer the internal `notes` tool: the agent's own notes for the chat, kept as short labelled lines in `notes.json` in the chat's evidence directory (`.themis/context/<chat>/`). A line has a key (at most 60 characters), text (at most 300) and, for task lines, a status (`pending`, `in_progress` or `done`). A call sends only what changes: `set` adds or updates lines by key (a status-only update keeps the text), `remove` deletes keys. Notes hold at most 80 lines and 8 KiB rendered; oversized lines or notes are rejected with a request to shorten them, never truncated. Control characters become spaces, so a note cannot forge the end of its block. The tool touches nothing else and needs no approval. The system prompt asks the model to start multi-step work with a notes call: a `goal` line, one line per task with its status, and every result needed later (counts, names, decisions, paths; a total over many items is kept as a running total updated per item), updated as each item finishes and kept until the whole task is done. It does not prescribe an order of work: reading everything first is fine when the notes keep what will be needed.

Notes are shown to the model in three places: just before the current request at the start of every run (so a later message in the chat, which otherwise only carries text turns, still sees the goal and progress), in full in every context checkpoint (as fixed content, before cache allowances are sized, so shrinking caches never drops them; a checkpoint without notes carries a hint to start them, and one whose summarised span had three or more tool calls but no notes update carries a hint to update them with what was finished and found), and in each `notes` call's result (line count and open task keys). Restored checkpoints drop their stored copy, so only the current file is shown. Once per run, after three tool calls in a chat that still has no notes, the next tool result carries a `notes_reminder` to start them; one- and two-call tasks never see it. If the agent kept notes during a run and then tries to finish while task lines are still `pending` or `in_progress`, the runtime sends it back with the open keys (`[Runtime check, not from the user]`); it then finishes them or marks them done or removes them with a reason. A later check comes only if the agent made tool calls since the previous one, at most three per run, so a model that drifts into narration ("Let me continue…") is pushed back to work while narration right after a check still ends the run. The system prompt also tells the model that a reply without tool calls ends its turn, so progress updates belong in the same reply as the next tool calls. A run that answers without any tool call while task lines are open (for example one that only announces its next step after "continue") is also sent back once: it must do the work if the user asked for it, or keep the lines open and answer if the message was only a question or asked it to wait. A run that used tools but not notes is not held back. Notes are model-written: untrusted data shown as such, never instructions or permissions. A corrupt or oversized notes file loads as empty, without its invalid lines.

Checkpoints carry one runtime-owned task ledger, independent of the model-written summary. It is a single bounded block of JSON lines tagged `action`, `read` or `location` (older checkpoints may also hold `plan`):

- `plan`: written only by checkpoints from before the notes tool. Such a plan is read once and migrated into notes (lines `step-1`, `step-2`, ... with their status); new ledgers no longer carry a plan.
- `action`: completed non-read tool calls, with up to 512 characters of public intent and arguments, up to 1,024 characters of output, and the original snapshot, record and JSON pointer. This includes tools retained in recent messages.
- `read`: older successful bounded reads with their excerpt and coordinates, including the archive pointer to the original native read receipt.
- `location`: the coordinates of an older read whose excerpt no longer fits.

Space is assigned in priority order: the newest completed actions (at most 8,192 bytes and one twelfth of the allowance), then a location for every older read, then full excerpts for the newest reads with the remaining space (at most 64,000 bytes, scaled down with the context allowance). Eviction shortens action excerpts, then turns read excerpts into locations, then drops the oldest entries. Reopening a location's receipt recovers an earlier observation even if the live repository file changed; the receipt is JSON text, and its source excerpt offset is not a receipt offset. Entries are deduplicated across checkpoints, survive repeated checkpoints and persisted checkpoint restoration, and are parsed only from runtime-written checkpoint messages, never from user text. Checkpoints written before the ledger (separate completed-action, bounded-read and evidence-location blocks) still restore into it. Ledger entries are historical untrusted observations: not proof that current files still match, that work succeeded, or that a claim is supported. Earlier details stay in originals.

Because the ledger records observed actions, the model-written checkpoint keeps four sections: `Goal/constraints:` (goal, user constraints, every decision with its reason and findings still needed, with source pointers; the summarizer is told to scan the whole span, not only its start and end), `Unresolved work:`, `Parked work:` (other topics or tasks that were paused but not finished, each with key facts, decisions with reasons and pointers; `none` when there are none) and `Next action:` (what to do if the user continues this task). Validation accepts the four-section form when `Parked work:` is present and otherwise the three-section form; older three- and five-section checkpoints remain valid.

Checkpoint assembly budgets the task ledger against the actual serialized fixed messages. It targets continuation headroom of half the message allowance remaining beyond instructions and the active request, or 20% of the overall message allowance, whichever is larger, when mandatory state fits within that target; cache allowances shrink on overflow. If mandatory summary/recent context itself exceeds that target, it remains intact, so this headroom is a target rather than a guarantee. With saved originals, completed invocation arguments above 2,048 bytes become historical receipts with a 512-character preview and exact archive coordinates, including recent retained invocations. Pending calls are not offloaded, and executed writes are never truncated. The latest restored invocation also retains up to 512 characters of its public intent, and the fixed checkpoint header notes that the task ledger records observed actions. Prepared artifacts retain their pending execution/verification intent; a successful write is not evidence of execution or correctness. This uses public assistant text only, never private reasoning, and grants no permissions. Active instructions and required narrative are not silently cut to make caches fit; if mandatory context still exceeds the allowance, the run fails explicitly and preserves originals.

Within a run, previously seen native read/list/search observations receive a bounded reminder to reuse findings and take the next unresolved action, including alternating reads and native read path aliases. Shell reminders require consecutive identical arguments and output. The tools still execute; changed output or a different range gets a fresh observation. The reminder and preview obey the shared result-delivery byte allowance. This is exact repetition detection, not semantic loop prevention. The archive-specific hard recovery guard remains in effect.

`apply_patch` accepts numbered unified diffs, with a valid example in its schema, and forgives the mistakes models commonly make: hunk line counts are taken from the hunk body (the header's counts are ignored), each hunk's old lines are located nearest the declared start line, a match that differs only in whitespace is used when it is the only one in the file (context keeps the file's own text), and a tab-indented context line missing its leading space is read as context. Old lines that are absent or match only ambiguously still fail with nothing changed, and the error shows the file's actual lines near the declared position. Unsupported nonempty formats fail rather than reporting an empty successful edit; larger generated edits can use approved Python/bash.

Malformed tool-call JSON is rejected before execution. When sending that rejected call back as history, all provider protocols wrap the raw arguments in a valid `_themis_rejected_tool_arguments` object, retaining the call ID and error result. Stored history and original snapshots keep the exact rejected arguments. This prevents an invalid historical call from breaking the next provider request; it never repairs or executes the malformed command. A corrected call still goes through normal validation and approvals. Python errors and failing tests remain process failures for the model to inspect and correct.


The shared server also selects bounded original exchange anchors from the durable transcript for latest-task follow-ups, lexical older-topic recall and a requested topic index. Entries include source sequence, role and excerpt coordinates; they are historical quotations, not new instructions or permission. Decision status remains unclassified unless the actual wording establishes it. Latest chronological exchanges anchor vague follow-ups; explicit current requests can resume an older topic. This deterministic retrieval is lexical, not a semantic guarantee; chaotic-task routing and held-out topic recall require live evaluation. Finished and incomplete handoffs are both retained. See configuration for content-free usage telemetry and the get_context_usage API.


Newly attached UTF-8 `.txt` and `.md` documents receive complete semantic preparation before ordinary generation. All selected documents count toward a 64 MiB batch bound. Sources up to 4,096 bytes use a durable verbatim capsule without a model call; larger documents use the same ordered source-stage, validation, automatic retry and consolidation pipeline as context checkpoints. A fitting document uses one request. The configured internal document input budget is independent of ordinary context and clamped to the routed summary model capacity. This does not enlarge the ordinary conversation window.

Each uncached document has its own `compaction.timeout_seconds` job deadline (default 900 seconds), shared by its stages, requests, retries and waits. The whole batch has a separate `compaction.document_batch_timeout_seconds` bound (default 3600 seconds, maximum 21600), including source saves, cache lookups and publication. A smaller remaining batch budget caps a fresh document job. The caller's Stop signal cancels either scope. Summary 429 backoff starts at configurable `compaction.rate_limit_backoff_seconds` (default 10 seconds), doubles on the second retry and adds jitter, while honoring a longer Retry-After floor. There are still at most two retries; neither deadline nor retry counters reset per attempt. Completed capsules and exact content-addressed JSONL originals persist even if a later document fails; no partial batch is installed in the current working context. Pending metadata records source hash, pipeline, routed model, captured configuration and effective input/output allowances. Matching stages and capsules are reused automatically, including after execution-only deadline/backoff/retry configuration changes. Cache keys bind the resolved prompt, source, routed model, effective input/output policy and pipeline. Exact known legacy keys can be migrated after validation when no custom resolved prompt is active; arbitrary historical settings are not guessed. Bounded stage files are validated before create-new promotion, and the old evidence stays unchanged. Diagnostics report job and batch limits, remaining batch time, capsule migrations and reused stages without source text. Exact quotations require reopening original record 1, `/content`; semantic processing coverage is not a guarantee of factual retention.

Capsules remain in the existing transcript store across turns/restarts. Reattachment requires matching source bytes/hash, path association, pipeline, summary model and policy. Current attachments replace their exact path association in historical capsule selection for that request. Later lexical name/path/hash recall searches the catalog before bounded body selection. Distinct same-name uploads retain separate path/hash identities; the harness does not infer that one supersedes the other. Thread deletion removes its capsule rows. Document preparation requests contribute to the run's usage totals, and capsule content has its own distribution bucket. Diagnostic logs contain hashes, sizes and activity metadata, never document text.

### Topic switches and short replies

- **Gated deferral before social messages.** When the new user message is a greeting, thanks or farewell with no task in it (at most 200 characters, no attachments), the first request of the run skips semantic compaction as long as the calibrated request plus the growth forecast still fits the hard input budget (usable message tokens after tool schemas, the output reserve and the safety margin). Short task messages ("fix the auth bug"), bare acknowledgements ("perfect", "great, continue") and mixed messages ("hi, fix the auth bug") compact as before. Maintenance is unaffected, overflow recovery still compacts, and the next turn after any large observation compacts normally; the checkpoint otherwise happens on the next substantive turn. The decision is captured per run (the desktop marks it from the raw user text and attachments, not from the composed task) and recorded as the `compaction_deferred_short_reply` activity and diagnostic.
- **Anchors need content.** `themis_core::social` decides what is social: every token is a social word or a neutral filler with at least one social word (multilingual lists; combining marks stay inside words; Chinese, Japanese, Korean and Thai phrases match whole phrases at token boundaries, never single characters inside a content word). Social messages get no history anchors. "continue", "ok", "perfect" and mixed messages keep the latest-exchange anchor. Lexical recall terms need three characters in spaced scripts and two in unspaced scripts after removing leading/trailing social phrases, at most twelve per request. An anchor already verbatim in the working context is not injected again (substring match for excerpts of 40+ characters, whole-turn match for shorter ones).
- The checkpoint prompt treats the user's latest short or conversational message as a possible topic switch, keeps the topic being worked on as the main task and every other unfinished topic as parked work.
