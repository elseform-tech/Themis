# Compaction checkpoint evals

A repeatable measurement of how much a conversation keeps after Themis compacts it.
This is a **live-model benchmark audit**, separate from the automated runtime checks.
It is never run in CI against a real model; CI only proves the plumbing offline
(`python -m unittest evals.compaction.test_harness` and
`cargo test -p themis-core --features eval --test compaction_eval`).

## How it works

1. `crates/core/src/runtime/eval.rs` (cargo feature `eval`, never in releases) replays a
   fixture transcript and **forces** one compaction after each chunk boundary through
   the same internals a run uses (`compact_context_with_evidence`, with saved originals),
   so repeated compactions exercise prior-checkpoint carry-over.
2. After the last compaction every probe question is asked using only the post-compaction
   working messages: no tools, no archive access. Answers must be short or exactly `UNKNOWN`.
3. `python3 -m evals.compaction run` grades answers deterministically and writes
   `evals/compaction/results/<date>-<model>-<budget>.json`.

The runnable is `crates/core/examples/compaction_eval.rs`
(`required-features = ["eval"]`); the harness builds it for you.

## Run

```sh
export OPENCODE_KEY=...   # never commit or print it
python3 -m evals.compaction run --suite core --trials 3 \
  --model longcat-2.5-preview-free --budget 24000
```

Options: `--case NAME` (repeatable), `--jobs N` (parallel runs, default 3),
`--recent N` (verbatim tail messages, default 20 like the app), `--timeout S`,
`--base-url URL` (mock provider; no key needed), `--runner CMD` (skip the build), `--out FILE`.
Run a single case directly with
`cargo run --release -p themis-core --features eval --example compaction_eval -- --case evals/compaction/cases/<name> --model M --budget 24000`.

## Grading

Per probe: `correct` (an `any_of` substring or the `regex` matches, case-insensitive),
`unknown` (answered `UNKNOWN` for a fact that was in the conversation: forgotten),
`stale` (matches a `stale` pattern of a superseded value and not the current one),
`wrong` (neither), `error` (provider failure). A truncated probe answer is retried once
with a larger output cap; remaining `error` probes are counted under `probe_errors` and excluded
from every retention rate, since a failed request says nothing about what the checkpoint kept. Decoy probes ask for facts that were never
stated; any answer other than `UNKNOWN` counts as `invented`.

Reported, as mean and sample SD (plus min/max) across trials: **summary-only retention (the
headline)**, which counts only probes whose planted record is no longer verbatim in the
post-compaction context (the runner reports `verbatim_records` from the actual working
messages), tail retention (record still verbatim) and overall retention, then per
category and per position (early/middle/late third of the transcript by where the fact was
planted), stale-fact rate (over probes that define stale patterns), forgot rate, wrong
answers, invented decoy answers, compaction latency, estimated tokens before/after, and
provider requests per compaction. Decoys never count towards retention. `failed_runs` lists
runner crashes/timeouts and `invalid_runs` lists trials whose compaction failed (probes would
have been answered from uncompacted history); both are excluded from the statistics.
Category and position breakdowns use the summary-only basis (`*_overall` keys have all probes).
`python3 -m evals.compaction regrade <result.json>` re-grades stored answers offline with the
current grader and fixtures.

Grading is lexical: a correct paraphrase that avoids every expected pattern is scored wrong,
and a hedged answer that names the new value passes even if it also mentions the old one.
Treat small differences between runs with a single trial as noise.

## Cases

`cases/<name>/` holds `transcript.jsonl`, `probes.json`, `case.json`.

- `transcript.jsonl`: one record per line: `{"role":"user"|"assistant","content":...}`,
  assistant tool calls `{"role":"assistant","content":"","tool_calls":[{"id","name","arguments"}]}`,
  and tool results `{"role":"tool","results":[{"id","name","output"}]}`.
- `case.json`: `name`, `kind` (coding, parked_topic, superseded, narrative), `suites`,
  `records`, `chunks` (ascending record counts after which a compaction is forced; the last
  covers the whole transcript) and `next_action`.
- `probes.json`: `id`, `category`, `question`, `planted_at` (1-based number of the record that itself states the
  fact; sets the position bucket and the verbatim check; `gen_cases.py` asserts that the record
  matches `expected` or the optional `needle`), `expected` (`any_of` and/or `regex`), optional `stale`
  regexes, or `expect_unknown: true` for a decoy.

Fixtures are synthetic and generated by `python3 -m evals.compaction.gen_cases`
(facts hand-written, filler generated from a fixed seed). To add a case, write a builder in
`gen_cases.py`, register it in `main()`, regenerate, and commit the output. Keep each chunk
below the budget (about 12-15k estimated tokens for the 24k budget) and plant facts early,
middle and late. Run `python3 -m unittest evals.compaction.test_harness`; it checks fixture
shape and the Rust test replays every case.

## Behavior evals

`python3 -m evals.compaction behavior --trials 3 --model M --budget 24000 [--anchors old|new]`
measures what the agent does with the next user message after a compaction. The
`behavior_eval` example (feature `eval`) compacts a text-only conversation like the retention
runner, then plays every turn of `behavior.json` through the real agent loop (all tools offered,
every approval denied; `recall` is offered as in the app when the tree has it) on top of the post-compaction context, and reports the reply, attempted
tool calls and checkpoints. Cases use `"suites": ["behavior"]`:

- `behavior-greeting`: "hi", "thanks!", "你好", "hey, how's it going?" after an unfinished task:
  short reply, no tool calls, no compaction, no mention of the task.
- `behavior-unrelated`: unrelated questions are answered and the task is not touched.
- `behavior-topic-return`: topic A, compaction, topic B, compaction, then "back to A" (or B):
  share of the planted facts in the reply.
- `behavior-continue`: "continue" / "ok go on" / "keep going" resume the latest task, not an
  older parked topic.
- `behavior-no-redo`: the data format, its documentation and the reference values were read and
  recorded before the compaction; "continue", a goal turn and "keep going" should start the
  recorded next action, not read those sources again. Each tool call is graded `progress` (a write
  matching the task), `redo` (re-reading a recorded source) or `other`; the headline is the first
  call, because every approval is denied and the folder is empty, so later calls react to that.
  Reported as `first_call_redo_rate`, `first_call_progress_rate`, `redo_calls_per_turn` and
  `no_redo_pass_rate` (progress, and the first call is not a redo).

`--anchors old` reproduces the previous desktop behavior (latest exchanges injected as
historical anchors for every message); `new` omits them for turns marked `social` and when the
text is already in the working context. The desktop store itself is covered by
`crates/desktop/tests/transcript_store.rs`. Grading (`behavior.py`) is lexical. CI only runs the
scripted-provider versions (`evals.compaction.test_harness`), which prove plumbing, not model
behavior.

## Mid-turn re-read evals

`python3 -m evals.compaction midturn --trials 4 --model M --budget 24000 [--turns 40] [--effort max]`
runs a whole task from an empty conversation (`redo_eval` example, feature `eval`): the case's
`project/` is copied into a temporary folder, the task in `task.json` runs with every file tool
allowed and `shell`/`git` denied, and the budget is small enough that the run compacts while it
works. The live catalog's output limits apply, as in the app. `redo.py` counts a re-read when the
same slice of a file (path, offset, limit, find) is read again after a checkpoint without the
file having been written since; reads of the run's own saved outputs (`.themis/`) count apart.
Reported: checkpoints, calls, reads, `rereads_after_checkpoint`, `reread_share` (re-reads over
reads after the first checkpoint), `repeated_reads` (no checkpoint in between) and
`outputs_written` (of the files `task.json` lists).

## Recorded results (2026-10-20)

`results/2026-10-20-behavior-*` test a checkpoint-envelope nudge ("when resuming, start from its
next action and re-read a source it records only for detail it lacks or when something
contradicts it"), with minimax-m3.1-flash-free at a 24k budget. `-main` is main at the time; `-nudge`
adds the clause (branch `codex/checkpoint-nudge`, not merged).

- `behavior-no-redo`, 8 trials × 3 turns per arm: no first call re-read a recorded source in
  either arm (0/24 each); turns with any re-read: 0/24 main, 1/24 nudge. The case does not
  reproduce the live re-research (one checkpoint, default effort), so it cannot show a benefit,
  and the nudge was not shipped.
- `behavior-no-redo-chain-max-*`: the research four compactions back (five compactions in all),
  `--effort max`, 6 trials × 3 turns per arm: 0/18 first-call re-reads and 0/18 turns with any
  re-read in both arms; every final checkpoint kept the format facts (`facts_retained_rate` 1.0).
  Every turn started by listing the project. Chained compactions and max effort did not
  reproduce the live re-research either. The live runs differed in compacting mid-turn at a
  100k budget, with downloaded copies outside the project, so the re-reads there may have been
  for detail (exact column offsets) that a checkpoint does not keep.
- `midturn-*` (case `midturn-ephemeris`, 24k budget, 40 model turns, 4 trials per arm; one run
  per arm timed out and is excluded): main averaged 11 checkpoints, 30 re-reads and a re-read
  share of 0.75; the nudge 7, 19 and 0.67, with wide spread (n = 3). No run in either arm wrote
  any of the three files: each read whole data files at 8,000 characters a page, filled the
  budget, compacted and read them again. The nudge does not break that loop. An earlier round
  without the catalog's output limits died on truncated replies and is not recorded.
- `behavior-guard-*`: the four older behavior cases, 2 trials per arm, as a regression check
  (greeting pass 0.125 main vs 0.25 nudge; unrelated 0.83 vs 1.0; topic return 1.0 vs 1.0;
  continue 0.83 vs 1.0). Too few trials to read as a difference. Note that this model resumes the
  task after most greetings in both arms.
